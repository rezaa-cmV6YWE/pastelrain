# Repository Guidelines

## Project Overview

`pastelrain` is a TanStack Start app (React 19, SSR) deployed to Cloudflare Workers. It was scaffolded with create-tanstack-app (`.cta.json`: file-router, Tailwind, `cloudflare` add-on, no examples). It is a scroll-driven storytelling portfolio. The single `/` route renders `<SceneDefs />` once, then four scenes, each pinned in its own scroll track:

1. `CrossingScene`: a paper-cut SVG seaside railway crossing with pointer parallax, in a five-screen track. The title fades, narration captions play, a local train sweeps in from the right and brakes to a stop with a window in front of the camera, which zooms in until the train fills the screen. Reaching the end plays (not scrubbed) a rush zoom into that window: its glass clears to show the train interior, and once it covers the screen only the train scene remains. Scrolling back up plays it in reverse.
2. `TrainScene`: a first-person view inside the train, facing the windows on the sea side, in a track whose height follows from its timeline. It is pinned beneath the crossing's end, so it shows through the window during the rush and the switch has no cut. A book, held up close (its bottom quarter runs past the screen's bottom edge), rises and tells who Rezaa is, page by page; it closes, the camera zooms into the centre window, and the train passes two stations whose signs show his work history. The light moves from noon to golden hour throughout. Past the last sign the sea keeps passing while the sun sets to dusk, and the platform pulls in from the left in front of that same sea (nothing fades), braking with its station-name board in the centre window (`pullIn`). Reaching the end plays a second rush (`arrival`) through the centre window onto that platform.
3. `PlatformScene`: a station platform at dusk, seen first-person facing the station wall, in a track whose height follows from its timeline (and the number of projects). It arrives facing the station-name board; you pull out a phone, and page scroll drives its feed of project cards (picture, kind · year, title, summary, stack, links; "More" pushes the project's page, with the full description, inside the phone like an app screen). The phone goes away, and a walk sideways along the platform ends at the ticket gate, which the camera goes through as its paddles open, ending on the dusk sea.
4. `BeachScene`: the same shot goes on, with no cut. The camera pushes past the gate into the sea, then pulls back as dusk turns to night, revealing the beach. Paper fireworks go off over the sea, a melancholy closing line ("The fireworks always end too soon." / "Thank you for staying until the last one.") is revealed in the centre of the sky like the opening title, and the contacts fade in at the bottom-right: "Say hello" over a row of logo links. The beach is drawn in the platform scene's view and camera (the same `DuskSky`); `BeachScene` owns the scroll track, the closing line, the contacts and `shore`, its scroll progress.

`README.md` is empty, and there are no server functions, loaders, data fetching, or app state yet.

## Architecture & Data Flow

- **Request path:** Cloudflare Worker (`wrangler.jsonc` → `main: @tanstack/react-start/server-entry`) → TanStack Start SSR → router from `src/router.tsx` → route tree in `src/routeTree.gen.ts` → route components in `src/routes/`.
- **Root shell:** `src/routes/__root.tsx` uses `createRootRoute({ head, shellComponent: RootDocument })`.
  - `head` sets the title, description, theme colour, canonical link and Open Graph/Twitter card tags, and links the CSS via `import appCss from '../styles.css?url'`. Social cards need absolute URLs, so `site` (`https://pastelrain.com`) prefixes the canonical link and the card image, `src/assets/og.jpg` (1200×630, a screenshot of the crossing's opening frame with the title shown; retake it if that frame changes).
  - `RootDocument` renders `<html>`, `<HeadContent />`, `<ReactLenis root />`, the children, TanStack devtools (only in dev, `import.meta.env.DEV`, trigger at the top-left so it stays clear of the contacts), and `<Scripts />`.
- **Router:** `src/router.tsx` exports `getRouter()`, which is the Start convention; do not rename it to `createRouter`.
  - Options: `scrollRestoration: true`, `defaultPreload: 'intent'`, `defaultPreloadStaleTime: 0`, `defaultNotFoundComponent: NotFoundPage` and `defaultErrorComponent: ErrorPage` (`src/components/halt-scene/`). Being router defaults, they also cover a route without its own `notFoundComponent`/`errorComponent`, and the root's render inside `RootDocument`. An unmatched URL answers 404 on SSR; the root `head` reads the root match's `_notFound` (router-core's only flag for a global not-found) to title it "Not on this line · Re:" with `robots: noindex`.
  - The `declare module '@tanstack/react-router' { interface Register { ... } }` block provides type-safe links. Keep it.
- **Vite plugin order** (`vite.config.ts`), which matters: `devtools()` → `cloudflare({ viteEnvironment: { name: 'ssr' } })` → `tailwindcss()` → `tanstackStart()` → `viteReact()`. `resolve.tsconfigPaths: true` is enabled.
- **Analytics:** Umami Cloud (cookieless, so no consent banner), configured in `src/analytics.ts`. `head` loads its tracker only in production (`import.meta.env.DEV` off), and `data-domains` limits it to `pastelrain.com`, so `pnpm preview` on localhost records nothing. Clicks are `data-umami-event` attributes: `contact` (`contact`: the label), `project-link` (`project`, `link`, `from`: `card` or `page`) and `project-more` (`project`). Scroll milestones go through `useMilestone(event, value, at)` in `src/routes/index.tsx`, sent once per load: `reach-train` (`handoff` 1), `reach-platform` (`arrival` 1), `reach-beach` (`shore` at the end of `throughSpan`), `reach-contacts` (`shore` at `contactsStart`). Never unsubscribe from a motion value inside its own change callback: Motion then skips the next subscriber for that change (two milestones on `shore` crossed in one jump lost the second), so `useMilestone` unsubscribes in a microtask. To test it, load the preview with an init script that removes the tracker's `data-domains` and stubs `fetch` for `/api/send` so nothing reaches Umami.
- **Styling:** Tailwind v4, CSS-first (`src/styles.css`: `@import 'tailwindcss'` plus an `@theme` block). There is no `tailwind.config.*`.
- **Animation:** the `motion` package (`motion/react`). Follow `.agents/skills/motion/` guidance.
- **Smooth scrolling:** Lenis (`lenis`, `lenis/react`) is mounted once as `<ReactLenis root />` in `__root.tsx`, and its stylesheet is `@import`ed in `src/styles.css`.
  - It smooths wheel and trackpad scrolling on the window. Touch keeps native scrolling.
  - `lenis.stop()` holds scrolling (the crossing's opening move, the rushes into the train windows, an open project page in the phone). Lenis does it with `overflow: clip` on `<html>`, which removes a classic scrollbar and changes the page width mid-motion; `src/styles.css` overrides it on `(pointer: fine)` devices with `overflow: hidden` in a `scrollbar-gutter: stable` gutter, so the width stays put. Its selector must out-rank Lenis's `.lenis:not(.lenis-autoToggle).lenis-stopped`.
  - It turns itself off for `prefers-reduced-motion` (`respectReducedMotion`, on by default).
  - Motion's `useScroll` reads the window scroll, so scroll-driven scenes follow the eased scroll automatically. Don't add a second scroll container.
- **GPU memory:** each `ParallaxLayer` (and any other animated full-screen element) is its own composited layer, about 24 MB of tiles at 2× DPR. When too many draw at once, Chromium browsers run out of tile memory and show rectangles of the scene missing or stale, which can persist after the busy moment. So scenes don't draw what can't be seen: the train scene's two views are `visibility: hidden` until the hand-off starts and again once the arrival ends, the platform's view until the pull-in starts (and its sky until the arrival starts), the platform's own planes once the beach takes over and the beach's planes until then (`onPlatform`/`onBeach`), the crossing's view once it ends, and during the rush the crossing's planes behind the stopped train (`covered`). Never put `will-change: transform` on anything inside a zooming camera: Chromium keeps a will-change layer drawn at the largest scale it has been zoomed to and never lowers it, so after the zooms and the rush the planes stayed drawn at ~3× (255 MB of tiles at the top of the page instead of 40 MB; past the budget the gates and signals went undrawn and flickered, and scrolling up ran at half speed). The planes get their own layers anyway. The exceptions are the platform's walking strips, which have `will-change: transform` only while the gate camera is at 1× before the beach (`Walk` in `platform-scene/strip.tsx`; never on iOS, see "Safari filters"), and WebKit's filtered art (see "Safari filters"; WebKit redraws a zoomed layer at its new scale either way). To reproduce, launch Chromium with `--force-gpu-mem-available-mb=192`, scroll with the wheel through the rush and back up to the top, and compare with a fresh load; the compositor's `LayerTreeHostImpl:snapshot` trace event (`disabled-by-default-cc.debug`) gives each layer's `gpu_memory_usage`. CDP's `LayerTree.compositingReasons` tells which elements have their own layer.
- **Frame rate:** SVG and CSS filters re-run whenever their layer repaints or is drawn at a new zoom, which made every zoom and the moving train stutter. So scene art gets its rough paper edge from geometry (`scene-kit/rough.tsx`), not the `#pr-cut` filter, which is left to HTML text (`.pr-cut-text`). The `pr-paper` drop shadow's blur is `--pr-paper-blur`, which each scene's view sets to 0 while its camera zooms or rushes (`usePaperBlur` in `scene-kit/camera.tsx`): the zooming planes are redrawn at every new scale, and the blur held the crossing's zoom at ~37 fps and the gate's at ~43 (2× DPR, M2); with a hard shadow every part of the page measured 60 fps. Give any new camera move its progress in `usePaperBlur`. Don't read layout (`getBoundingClientRect`) every frame of an animation: the scenes' CSS animations dirty style each frame, so each read forces a full style and layout pass (measure once, as the rush does). SVG `<text>` needs `textRendering="geometricPrecision"` (see `stations.tsx`). To measure, use a production build (`pnpm build && pnpm preview`) in a visible GPU browser at 2× DPR; a headless one misses GPU costs.
- **Safari filters:** WebKit draws CSS filters in software and redraws them whenever the filtered art repaints, and a zooming camera repaints its art at every new scale. In Playwright's WebKit (393×852 at 3× DPR, M2) the crossing's zoom ran at 3–6 fps, the rushes at 2–3 fps and the station run at ~4 fps, with frames up to 2 s. So `src/styles.css` gives every `.pr-paper` SVG and the book's paper (`.pr-cut-text:empty`) its own layer in WebKit (`@supports (font: -apple-system-body)`), where Core Animation draws a lone drop-shadow, and cut text drops the `#pr-cut` displacement there (software-only); afterwards every part measured 42–55 fps. Those layers double the layer memory, and iOS has no room for it: an iPhone 15 showed "A problem repeatedly occurred" (iOS killed the page's process) in the rushes, the reverse rush out of the train window above all, both with the software shadows (huge filter buffers for art zoomed ~40×) and with the layers (layer memory peaked at ~1.2 GB in the reverse rush against ~0.45 GB without). So on iOS (`@supports (-webkit-touch-callout: none)`, every iOS browser; desktop Safari and Playwright's WebKit don't match it) the paper art and cut text have no filter and no extra layer: no paper shadows there, ~55–60 fps. The platform's walking strips (`.pr-walk`) get no `will-change` layer on iOS either: each is wider than the screen, and with it a fast scroll back up from the beach crashed an iPhone 15 in the train → platform rush every time, and the phone, the walk and the gate zoom each began with a ~470 ms frame; without it the same runs finished at 52–60 fps. The platform sky's clouds hold still for the same reason (drifting, its two strip-wide cloud layers cost ~300 MB in WebKit at iPhone size). Crashes like these only show on a real iPhone: Playwright's WebKit on a Mac didn't reproduce them. To test on the phone, serve the build on the LAN through a proxy that injects a script scrolling the page by itself and posting its progress back, and count a second load in the same tab (`sessionStorage`) as a crash. New filtered art should use `.pr-paper`, a single drop-shadow, not another filter. To measure: Playwright's WebKit with that viewport, `window.scrollTo` in steps with rAF frame times, and `footprint -p` on its WebContent and GPU processes (re-scope the iOS block to `font: -apple-system-body` in an injected style to measure it there).
- **Mobile toolbar:** phone browsers collapse their toolbar on scrolling down and bring it back on scrolling up, which changes `window.innerHeight` (and `dvh`, the size of a `position: fixed; inset: 0` box, and in some browsers the root's `clientHeight`) and fires `resize`. Browsers built on an iOS web view (Arc) resize the whole web view instead, so there `svh` and `lvh` change too. So scene layout uses no viewport units and nothing reads the window's height: `useStableScreen` (`scene-kit/screen.ts`, called once in `src/routes/index.tsx`) sets two px heights on `<html>`, with `svh`/`lvh` fallbacks in `src/styles.css` for SSR. `--screen` (the viewport with the toolbar showing) is one screen of scroll and layout: track heights and their one-screen overlaps, the book, the phone, the title's and closing line's spots. `--view-h` (the viewport with it hidden) is the height of every scene's fixed view and `PaperGrain`: a view the height of the viewport with the toolbar showing left a blank strip below it once it collapsed, and with the toolbar showing the bottom of the scene sits behind or below it. With a coarse pointer both are measured again only when the width changes (turning the phone); `--view-h` otherwise only grows, to the tallest viewport seen, so in Arc the views grow once, at the first collapse after a load with the toolbar showing (one rescale), and never again. With a mouse every resize measures both. Scene progress comes from `useTrackProgress(track, screens)` (`scene-kit/track.ts`), worked out from the track alone, not `useScroll`'s `end end` offset, which measures against the root's `clientHeight`, so progress could jump as the toolbar toggled. Scroll positions for a progress (`useRush`'s end, the phone's and the contacts' focus scrolls) come from `trackScrollY`; computed from `innerHeight`, a rush's end fell short of progress 1 by the toolbar's height, so the first touch after the rush played it back out. `usePullInDistance` measures its scene's view, not the window. With the toolbar hidden the page ends a toolbar's height before the beach's progress reaches 1 (past every moment in it). Desktop browsers and DevTools device mode have no such toolbar (`svh` = `lvh` = `dvh` there), so check on a phone. To simulate Arc, resize a touch-emulated viewport's height (Puppeteer `page.setViewport`, applied before loading, or `(pointer: fine)` still matches at load); to simulate Safari, override `innerHeight` and `document.documentElement.clientHeight` in an init script and dispatch `resize`.
- **Hidden scenes do no work:** each scene's view sets `--pr-play` from its hand-off values (`paused` while it is hidden), which every `pr-*` animation in `src/styles.css` uses as its `animation-play-state`, and the train's cruise loop skips frames while `handoff` is 0 or `arrival` is 1. Give any new looping scene animation `animation-play-state: var(--pr-play, running)`. A function-form `useTransform` over several values must read them all before comparing (`a.get() > 0 && b.get() < 1` never subscribes to `b` while `a` is 0).
- **Safari stale text:** Safari kept drawing faded HTML text that carries the `#pr-cut` filter (`.pr-cut-text`) and per-letter animations as a stale layer, even under a hidden ancestor (the title's "Re:" blinked over the scene, inside the train too). So faded text is not rendered at all: the title's wrapper gets `display: none` once `titleOpacity` reaches 0, and each caption once its exit animation finishes. Reproduce with Playwright's WebKit, headed, with video recording.

## Key Directories

- `src/routes/`: file-based routes. `__root.tsx` is the document shell and `index.tsx` is `/`.
- `src/components/scene-kit/`: shared by every scene; import with `#/components/scene-kit/<file>`.
  - `palette.ts` holds every scene color; SVG fills reference `palette.*` rather than Tailwind tokens.
  - `scene-svg.tsx`: `SceneSvg` (shared `viewBox="0 0 1600 900"`, `xMidYMax slice`), `SceneDefs` (the `#pr-cut`, `#pr-glow`, `#pr-stripe`, `#pr-grain` defs that every layer references by URL; rendered exactly once, in `src/routes/index.tsx`, so ids never repeat), `PaperGrain` (the paper texture: one fixed multiply overlay above every scene, also rendered once in `src/routes/index.tsx`, so no grain swaps at the hand-offs), and `SceneHtml`: the 1600×900 stage laid over a `SceneSvg`, with the same bottom-centred cover mapping (via container query units; `--u` is one viewBox unit in CSS px), for HTML in viewBox units. `SceneHtml` clips with `overflow: clip`: an `overflow: hidden` box is still scrollable, and focusing a control in it scrolled the HTML off the art. Its box is a size container through Tailwind's `@container-size` utility. Don't write it as the arbitrary property `[container-type:size]`: `pnpm format` (oxfmt's class canonicalising) rewrote that to the invalid `@container-type:size`. With no container, `cqw`/`cqh` fell back to the window, every stage came out the window's size instead of its overscanned box, and the beach's sky left a 48px empty band at the top on screens narrower than 16:9.
  - `rough.tsx`: `Rect`, `Circle` and `Path` draw their shape as a `<path>` with rough paper-cut edges baked in: each segment is sampled every 7 units (densely enough on curves) and nudged by smooth 2D noise with the `#pr-cut` filter's strength. Use them for every static shape that should look cut from paper; plain `rect`/`path` stay smooth. The noise depends on position, so touching shapes wobble together and identical input gives identical output (a clip path matches the shape it cuts); it uses integer hashing and plain arithmetic only, so SSR and the browser write the same path data. Outlines are cached by input, so don't feed it geometry that changes every render. `Shift` is a `translate` group that also moves the noise, so repeated art (the train's two cars) doesn't share edges. `roughVertices(d)` reads a drawn outline's vertices back (the rush cuts the panes' exact shapes with it). The baked paths add about 60 KB (brotli) to the HTML.
  - `ease.ts`: `cinematic`, the long soft ease-out shared by the title and narration.
  - `reveal-text.tsx`: `RevealText({ text, active, delay })`, a line of text revealed like a film title card while `active`: time-based (not scrubbed by scroll), letters come out of a blur from the centre, and per-letter `x` offsets imitate letter-spacing closing in (so layout and wrapping never change; words wrap only at spaces). Turning `active` off blurs it out. It is only rendered while shown or leaving (see "Safari stale text"), so its screen-reader copy sits beside it. Used by the narration captions and the beach's closing line.
  - `handoff.ts`: the hand-offs' timing: `rush` (the transition both hand-offs animate with), `glareFade` and `glassFade` (crossing → train, in units of `handoff`), and `skyReveal` (train → platform, in units of `arrival`: the platform's own sky takes over from the train's outside mid-rush, while the carriage hides most of it; both are the same dusk colours). `handoff`, `arrival` and `pullIn` are motion values created in `src/routes/index.tsx`: the crossing plays `handoff` and the train scene's glass veil follows it; the train scene's scroll drives `pullIn` (the platform's share of its way into the windows, already eased), and the platform scene shows while it is above 0; the train scene then plays `arrival`, the rush through its centre window onto the platform.
  - `rush.ts`: `useRush({ view, track, progress, value, calm, target, onMeasure })`, the played hand-off both scenes use. When `track`'s scroll reaches the end it snaps to the exact end, holds scrolling (`lenis.stop()`), measures `target()` and animates `value` 0 → 1 (`rush`); scrolling back above the end plays it 1 → 0. A jump of more than half a screen past the end or back, and the position on mount (a restored scroll), set the state without playing. It returns a top-left-origin transform for the view's direct child: an exponential zoom about the target until it covers the screen (`coverMargin`), panning it to the centre. The target is measured once per play and on resize, never per frame. `target` and `onMeasure` must be stable (`useCallback`): a new function re-runs the effect, which stops a playing rush.
  - `drifting.tsx`: `Drifting`, a `pr-drift` wrapper around scene art (clouds; its child is usually a `SceneSvg`). `vignette.tsx`: `SeaVignette`, the small sun-over-waves picture on the book's chapter pages and on project cards without an image.
  - `color.ts`: `mixOklab(stops)` returns a `t → rgb()` blend through evenly spaced hex stops, each step a straight line in OKLab. Use it for scroll-driven colour changes between distant hues: Motion's own colour mixing is RGB, which turns grey halfway between blue and gold. Route such blends through a bright, pale stop (near-white reads as haze, not grey) rather than round the hue wheel, which goes pink or green.
  - `parallax.tsx`: the parallax Motion hooks (`usePointerParallax`, `ParallaxLayer`). A mouse or pen moves the scene while hovering. A finger moves it while touching and springs back on release. Touch listeners are passive and use touch events rather than pointer events, so they never block scrolling. `ParallaxLayer`'s optional `intro` (1 → 0) pushes the layer down by 25%–100% of its height depending on `depth`, which drives the crossing's opening crane shot.
  - `track.ts`: `useTrackProgress(track, screens)`, a scene's 0 → 1 scroll progress through its `screens`-screen track, and `trackScrollY(el, screens, progress)`, the scroll position for a progress. Use them, not `useScroll`'s `end end` or `window.innerHeight` (see "Mobile toolbar").
  - `screen.ts`: `useStableScreen()`, which keeps `--screen` (one screen of scroll and layout) and `--view-h` (the fixed views' height) on `<html>` still while a phone's toolbar moves. Use `var(--screen)`/`var(--view-h)` in scene layout, never `svh`/`lvh`/`vh`/`dvh` (see "Mobile toolbar").
  - `camera.tsx`: `useSceneCamera(progress, view, shot)` zooms a scene's camera exponentially, panning the focus from `shot.from` to `shot.to`. The final zoom is measured so a `shot.cover` box covers the viewport (times `shot.margin`); an optional `shot.keep` box caps it so that box stays fully in frame on screens shaped very differently from `cover`. Positions come from invisible `CameraMarks` circles, so the camera follows whatever framing CSS gives the scene, including the crossing's portrait box. `view` is the camera element's parent; measurements use its layout size and undo any outer translate/scale on it (the crossing passes the rush camera, `rushView`), so a resize mid-rush still frames correctly. `frame()` must read every motion value before its early return: function-form `useTransform` only tracks values it saw being read.
- `src/components/crossing-scene/`: the first scene.
  - `title.tsx`: the visible `h1`, revealed like a film title card. Letters fade up out of a blur, starting from the centre, while the word's letter-spacing closes in. The Motion variants take a `calm` (prefers reduced motion) `custom` value. `hidden` is identical either way, which keeps SSR hydration-safe. With calm, the letters only fade.
  - The layer components (`sky`, `clouds`, `sea`, `land`, `crossing`, `foreground`) use the `pr-*` animation classes from `src/styles.css` and draw with the `scene-kit/rough` shapes (the lamps' glows and lit faces stay smooth `circle`s). Never use `Math.random` in scene art, because it breaks SSR hydration.
  - `index.tsx` owns the scroll timeline (`useTrackProgress` over the five-screen `<section>`, `trackScreens`, with a full-screen view). Both scenes' views are `position: fixed`, not sticky: inside each scroll track that looks the same, but a sticky view slides with the page as soon as the scroll passes its section's edge, and at the hand-off the two views must stay exactly on top of each other whatever the scroll position (a sticky train view flashed a strip of blank page as the rush back out began). `handoff` alone decides which one shows. On load, `intro` animates 1 → 0 (`introDescent`: 0.3s delay, 3.2s): the camera lowers from the sky onto the crossing with per-layer parallax, then `Title` gets `show` and plays its reveal. User scrolling is held (`useLenis()` → `lenis.stop()`) until the camera lands; programmatic scroll restoration still works. Reduced motion skips the descent, and a position past `titleFadeEnd` (a reload partway down; checked on mount as well as on change, since restoration can land first) cuts it short. Cloud undersides are rounded puffs, not a flat cut, because the descent shows them above the sea. Pointer parallax stays live for the whole scene: the pointer values are divided by both cameras' zoom, so the on-screen sway stays the same size. The title fades out first. The train sweeps in from the right at 20%, cruises, then brakes (`brakeAt` → `trainStop`; an ease-out-quad, with `trainBrake` placed so the speed doesn't jump) to a stop with `train.focusWindowX` in front of the camera. The camera zooms from 65% to 100% (`crossingShot`). Every scene layer sits inside the scroll camera, which sits inside the rush camera (`useWindowRush`). While the rush plays (0 < `handoff` < 1) the planes around the stopped train are hidden (`covered`), and the view's sky background moves into the train's plane (`trainPlane`, the depth-28 layer's content, with a sky backdrop shown while `rushing`), which the rush clips. Once `handoff` reaches 1 the view gets `visibility: hidden`. The section is `relative z-10` so it stays above the train scene.
  - `window-rush.ts`: `useWindowRush` plays the hand-off with `useRush`, aiming at the `[data-glass]` pane nearest the screen centre. It also returns `clip`: once `handoff` is past `glareFade`, every pane is cut out of `plane` (the train's plane) with an evenodd `clip-path: path()`, so the train scene pinned beneath shows through. Each hole is the pane's exact rough outline (`roughVertices`, mapped into the plane by the pane's `getCTM()`), so the switch from navy glass to the navy veil behind it changes nothing on screen; holes cut as bounding boxes made the window's outline jump at that moment, a flicker on the way in and out. The stopped train doesn't move within its plane, so the holes are measured once per rush (and on resize; `onMeasure`) in the plane's own px; the zoom and the parallax carry them along. Measuring every frame instead cost the rush a third of its frames.
  - `train.tsx`: the two-car local train, drawn facing left, in the same paper-cut style as the rest of the scene. It uses the `pr-paper` drop shadow, rough shapes, solid-tone fills (no transparency) and a back sheet in a second tone. Each car is a `Shift`, so the edge noise is fixed to the train and differs between the cars. It renders between the far and near crossing fixtures through `Crossing`'s `track` slot. Window and door panes carry `data-glass` (the rush's target and openings); the reflection sweeps fade with the `glare` value. `focusWindowX` is the centre of the window the train stops in front of.
  - `narration.tsx`: the captions. Edit the `lines` array to change the story or each line's scroll window. They have no backing: they use the same paper-cut text look as the title, in navy. They are pinned to the sky: `Narration` renders inside the camera (with a box carrying the same 3rem overscan as a parallax layer), so at 1× it sits exactly in the title's spot and then zooms away with the world. Every line's window therefore ends by about 68%, just after the zoom starts. A line plays `scene-kit/reveal-text.tsx`'s reveal while its window is entered. It reuses `titleSpot` and `titleLine` from `title.tsx`.
- `src/components/train-scene/`: the second scene, inside the train.
  - `index.tsx` (`TrainScene`): the section is `relative -mt-[100svh]` with no z-index, so its scroll range starts at the crossing's end and its two fixed views stack on their own around the platform's view: the outside view (outside far at depth 4, outside near plus stations at 10) sits beneath it, so the station pulls in in front of the same sea, and the interior view (`z-5`) above it. Both sit beneath the crossing's view and show through the window during the rush; the navy glass veil clears with `handoff` (`glassFade`). The cruise is time-based (`useAnimationFrame` advances `cruise`, frozen under reduced motion) and slows to a stop as the zoom ends; after that, scroll drives `run`, which slides the stations past at a steady speed with no stops, on past the last sign until the pull-in takes over (`runEnd`). Scenery strips wrap a 1600-wide tile (`tile()`). The interior: a `pr-rattle` wrapper holding the carriage and sun patches (22), stanchions (32) and straps (40), inside the window camera, inside the arrival's rush camera (`useRush` into `Carriage`'s `[data-rush-target]`, the centre opening below the transom); the book sits outside both with the raw pointer. The outside view follows the window camera but not the rush camera: once the platform stands in the window the outside is behind it and stays with it. ## Code Conventions & Common Patterns

- **Formatting** is done by oxfmt (`.oxfmtrc.json`):
  - No semicolons and single quotes.
  - Imports are sorted automatically.
  - Tailwind classes are sorted, including inside `cn(...)` calls; the stylesheet entry for sorting is `src/styles.css`.
  - Never hand-format against it; run `pnpm format`.
- **Lint** is oxlint (`.oxlintrc.json`):
  - Plugins: eslint, typescript, unicorn, oxc, react, import, jsx-a11y.
  - `correctness` is set to error and `suspicious` to warn.
  - `react/react-in-jsx-scope` is off.
- **TypeScript** (`tsconfig.json`) is strict, with `noUnusedLocals`, `noUnusedParameters`, `noUncheckedSideEffectImports`, and `verbatimModuleSyntax`. Because of `verbatimModuleSyntax`, type-only imports need `import type`.
- **Path aliases:** `#/*` → `./src/*` works in both TypeScript and at runtime through `package.json` `imports`; prefer it. `@/*` is TypeScript-only. Existing code still uses relative imports.
- **Route file pattern:**
  ```tsx
  // src/routes/about.tsx
  import { createFileRoute } from '@tanstack/react-router'

  export const Route = createFileRoute('/about')({ component: About })

  function About() {
    return <main>…</main>
  }
  ```
  - Always export `Route`.
  - The path string must match the file location.
  - Define the component as a local function declaration.
- **Class merging:** use the `cn` package for conditional classes.
- **Fonts** come from `@fontsource` packages imported in `src/styles.css`, mapped to theme tokens:
  - `--font-title` (Shippori Mincho; applied to `h1`–`h6` in `@layer base`) → `font-title`.
  - `--font-sans` (Zen Kaku Gothic New).
  - `--font-mono` (JetBrains Mono Variable).
- **Cloudflare runtime:** `nodejs_compat`, `compatibility_date` 2025-09-02. No bindings or env vars are configured; add them in `wrangler.jsonc`. The worker name `tanstack-start-app` is still the scaffold default.

## Runtime/Tooling Preferences

- **Package manager:** pnpm only (v11; `pnpm-lock.yaml`). There is no `packageManager` or `engines` field. `pnpm-workspace.yaml` is a single package that only sets `allowBuilds` (esbuild, lightningcss, sharp, workerd).
- **Runtime:** Node for tooling; Cloudflare `workerd` for the server. There is no Bun.
- **Pinned versions:** `@tanstack/react-start` 1.169.4, `@tanstack/react-router` 1.170.46, and the devtools packages are pinned exactly. Upgrade them together.
